# Management usability and client plan selection

Approved discussion scope: items 1, 2, 3 and 5. Keep the existing deployment/auth
approach and official public routing policy. Do not add AI classification, an
auth-key UI, new authorization methods, or unfinished client format support.

## Management credentials

The deployer explicitly supplies MONOCLOUD_WEB_PASSWORD. Startup identifies the
management username admin and the password's environment-variable source without
printing its value. README describes this before server startup/browser login;
management credentials are distinct from MonoCloud account credentials. Change
the Basic realm to identify subscription management. No password is silently
generated by the application, and no interactive account CLI is added.

## Account presentation

Make subscriptions the primary page task. Put the MonoCloud login form in an
accessible expandable account section with a reconnect/switch-account entry.
Saved token alone is labelled as saved credentials, not verified login. The
management page verifies the account through service discovery on initial load
and after login. Valid credentials collapse the form; expired/rejected credentials
open it. A temporary upstream failure keeps saved credentials and does not force
a password retry. Retain existing safe login/storage handling and no secret echoes.

Keep the existing cheap /api/status behavior; optional verify=true returns an
account_state (signed_out/connected/expired/unavailable) and plan_count. This avoids
unnecessary API work for cheap status probes while supporting honest UI state.

## Client-side plan selection

Pass fetched Plan metadata into generate_clash as an optional keyword argument.
Generate a manual Proxy select group whose members are per-service manual select
groups; each child contains only that service's nodes. All nonempty services remain
in the subscription; there is no server-side plan picker or auto-switching. Use
plan names for labels, fallback Plan N labels, deterministic global collision
handling for groups/nodes/built-ins. Group by service_id, never by display name.

Keep Node/Plan types and existing per-node connection values. Keep original public
rules in order targeting Proxy/DIRECT. Tailscale stays outside the public selection
hierarchy and retains the same state path. Changing the hierarchy may reset an old
client node choice once; users should choose a plan/node after the first update.

## Guides

Organize the UI under client connection guides. Only Clash Mi is implemented now;
Surge and sing-box MT guides arrive with their format support. Avoid unusable tabs
or placeholder actions. Keep the current native frontend and ivory/green styling.
Store Clash Mi guide markup in a dedicated bundled resource, embedded by the server.
Its base flow covers reachable server URL/Wi-Fi, import, rule mode, plan/node
selection, updates and verification. Its optional Tailscale section adds capability
to the SAME URL/profile: enable/save, update/reconnect, existing log Copy menu,
authorization while VPN stays connected, Tailnet FQDN/IP and persistence checks.
No duplicated 'either/or' full workflows or log-upload/auth-key feature is added.

## Verification

Test grouping/membership/collisions, missing metadata/empty services, unchanged
rules/credentials, API orchestration, verified/expired/unavailable states, and
startup guidance without password output. Browser QA uses constructed credentials:
connected form hidden, reconnect entry works, signed-out/expired form visible,
upstream outage distinguished, guide readable on desktop/mobile. Run the full suite,
Ruff/build and both sanitized/actual HTTP core checks. Phone grouping revalidation
is recorded separately from the earlier flat-group acceptance.
